Interactive Dashboard Calculator to Enhance Operational Efficiency at Mechapres

This project was aimed at designing a prototype interactive dashboard calculator that will foster operational efficiency at Mechapres which is a small to medium-sized precision engineering company working in a resource limited manufacturing environment.

Tools: Python, Pandas, Plotly, Streamlit

  • Check it out

Executive Summary

This report shows how I applied a business analysis process to replace Mechapres’ manual heat pump feasibility estimates with a guided Streamlit calculator.

  • Problem: feasibility estimates were done by hand across disconnected tools, making them slow, error-prone and inconsistent.
  • Solution: an interactive calculator that automates the calculations and shows payback, IRR, NPV and CO₂ savings as low-to-high ranges.
  • Outcome: after deployment, less time spent on manual calculations, more consistent reporting and clearer visibility of cost drivers.

The work followed CRISP-DM, which aligns closely with the standard BA lifecycle. The stages were iterative, with findings from testing feeding back into the design several times.

1. Understand the Business Context

Mechapres helps industrial sites decarbonise steam production with high-temperature heat pumps. Its customers make large capital decisions, so each sale depends on a credible answer to one question: will this investment pay back, and when?

Key context I established:

  • Commercial pressure: tight margins mean small estimation errors affect pricing, profitability and competitiveness.
  • Resource limits: as a small business, Mechapres has limited IT capacity and budget for enterprise systems.
  • Decision-makers: the people using the outputs are often finance and operations leads, not engineers.

2. Define the Problem and Root Cause

Problem statement: Mechapres had no integrated, automated and interactive tool to turn its operational and financial data into timely, accurate feasibility decisions.

SymptomUnderlying cause
Estimates took too longCalculations done by hand, step by step
Errors in figuresManual data entry and formulas
Similar sites got different answersNo standard calculation logic across people
Customers struggled to read outputsResults were technical, not built for decision-makers

All four symptoms traced back to one root cause: manual calculations spread across disconnected tools.

Success criteria agreed with stakeholders:

  1. More accurate, consistent estimates
  2. Less time spent on calculations
  3. One consistent set of data and logic
  4. Outputs non-technical users can interpret

3. Stakeholder Analysis

I identified four stakeholder groups and what each needed from the tool.

StakeholderRole in the projectMain need
Project supervisorSponsor and subject-matter guideLogic that matches the business’s decision tree and customer needs
Production managersUsers and validatorsAccurate figures for resources and scenarios
Finance officersUsers and validatorsReliable investment metrics: payback, IRR, NPV
IT staffTechnical advisersA tool that fits a small IT footprint

Engaging these groups early meant the design reflected real working needs, which also built the trust needed for adoption.

4. Requirements Elicitation

I gathered requirements through structured consultations with stakeholders and through my supervisor’s ongoing design reviews.

Functional requirements

  • Automate the core feasibility calculations from user inputs
  • Show results as low-case and high-case ranges, not single-point estimates
  • Report investment required, payback period, IRR, NPV and CO₂ reduction
  • Flag cases that fall below viability thresholds
  • Update all outputs instantly when an input changes

Non-functional requirements

  • Easy for non-technical users to use and understand
  • Transparent, traceable calculation logic
  • Simple to deploy and maintain with limited IT resources

Scope: internal operational and financial data only. ERP integration and external data sources were deliberately excluded to keep the project deliverable.

5. Current State (As-Is) Analysis

The current state was a manual workflow: gather site data, calculate by hand in separate tools, then assemble results for the customer. To understand its weaknesses, I analysed the data behind it.

  1. Profiled the data: historical production, financial, material and labour records, using descriptive statistics (mean, median, standard deviation, range).
  2. Explored it visually: histograms, boxplots and scatterplots to spot outliers, skew and trends.
  3. Cleaned it: filled missing values with mean or median where appropriate, and separated real operational anomalies from data-entry errors.
  4. Integrated it: merged datasets held in different formats, and standardised names, units and time periods.
  5. Engineered metrics: derived unit cost, material efficiency, labour productivity and utilisation rates.

Key finding: the data existed, but its inconsistent formats and manual handling were the main sources of delay and error.

6. Future State (To-Be) Design and Gap Analysis

The future state is one guided tool where inputs, calculations and results sit together and update instantly.

Gap (as-is)Design response (to-be)
Calculations done by handRule-based, formula-driven logic in Python automates every calculation
Different logic per personOne standard calculation model for every case
Single-point estimatesLow-case and high-case ranges for all key metrics
Hard-to-read technical outputsA nine-page guided flow (Welcome to Results), cleaner labels, no excess decimals
Irrelevant inputs confuse usersConditional logic hides fuel inputs when an electric boiler or heat pump is selected
“When does it pay back?” unclearA 10-year cash flow chart with break-even annotations
Weak options not obviousAutomatic flags when a case falls below viability thresholds

7. Options Evaluation and Recommendation

Recommendation: a lightweight, custom Python and Streamlit application. It met the requirements at the lowest cost and IT burden.

OptionStrengthsWeaknessesDecision
Keep manual processNo new costLeaves every root cause in placeRejected
Enterprise BI or ERP-integrated systemPowerful, scalableHigh cost, complex, beyond a small IT teamRejected for now
Custom Streamlit applicationFast to deploy, low cost, fully tailored, transparent logicDepends on input data quality; no live system integration yetRecommended

Choosing a lightweight tool also kept integration open as a later phase, rather than a barrier to starting.

8. Implementation Support

I built the tool myself and refined it in short cycles, with stakeholder feedback after each round.

  • Validation: tested outputs against historical data and ran scenarios with changing production volume, material availability and labour allocation.
  • Defect fixing: resolved session-state conflicts that were resetting users’ inputs.
  • Usability refinement: removed technical parameter labels and excess decimals, and dropped early dynamic schematics that added clutter.
  • Structural redesign: moved from a tab-based interface to a nine-page guided flow, with a consistent blue professional theme and responsive typography.
  • Documentation: kept clear code comments on every calculation section so the logic stays traceable and maintainable.
  • Deployment and training: deployed on Streamlit and trained managers and staff to use the tool and interpret its metrics.

9. Evaluation and Monitoring

The tool met all four success criteria, based on quantitative testing, structured user tests with managers and finance officers, and monitoring after deployment.

Success criterionEvidenceResult
More accurate, consistent estimatesOutputs matched historical data; one logic applied to every caseMet
Less time on calculationsPost-deployment monitoring showed reduced manual calculation timeMet
One consistent set of data and logicIntegrated, standardised dataset and single calculation modelMet
Outputs non-technical users can readUser tests rated visuals and summaries as clear and relevantMet

Conclusion

By applying a structured business analysis process, I transformed a slow, inconsistent manual task into a reliable, customer-facing decision tool, achieved without enterprise systems or significant investment.

Next steps

  • Add predictive or optimisation models
  • Integrate with ERP and external data sources

Predictive Crime Analytics Dashboard, Visualising Crime Patterns and Forecasting Trends in Northern Ireland

This report explores the application of predictive analytics in the context of crime data analysis, specifically focusing on a dataset from Northern Ireland that includes various crime types and locations. The primary goal of this analysis is to build a predictive analytics dashboard that can assist stakeholders in understanding crime patterns and making informed decisions about resource allocation, law enforcement strategies, and public safety initiatives.

Tool: Python, Streamlit, Pandas, ARIMA

  • Check it out

Executive Summary

This report also shows the business analysis process used to build a predictive crime analytics dashboard for Northern Ireland, turning three years of public police data into hotspot maps, seasonal trends and a six-month forecast.

  • Problem: decision-makers in policing and public safety need to know where and when crime is likely to occur, but raw monthly police data does not show this directly.
  • Solution: an interactive Streamlit dashboard built on cleaned Data.police.uk records (May 2022 to April 2025), combining exploratory analysis with an ARIMA(1,1,1) forecast.
  • Outcome: the dashboard showed anti-social behaviour as the most reported crime, Belfast and urban centres as the main hotspots, and forecast rises in violent crime and burglary in colder months.

The work followed CRISP-DM, which maps closely onto the standard BA lifecycle. This was an academic project using public data, so stakeholder needs were defined from the business problem rather than gathered in interviews.

1. Understand the Business Context

Police forces and public bodies face growing pressure to make data-driven decisions about where to deploy limited resources. Predictive analytics can help by using historical data to anticipate future crime trends.

Key context I established:

  • Public data is available: Data.police.uk publishes monthly crime records for Northern Ireland, with crime type, month, location and coordinates.
  • Decisions are about resources: the main use of crime insight is deciding where and when to focus policing, patrols and prevention.
  • Ethics and law matter: crime data is sensitive, so GDPR principles such as data minimisation and the risk of bias in predictive policing shape what is appropriate.

2. Define the Problem and Root Cause

Problem statement: decision-makers in Northern Ireland had no single, accessible view of where and when crime happens, or how it is likely to change, to guide resource allocation.

SymptomUnderlying cause
Crime data is hard to interpretRaw records are spread across monthly CSV files
Hotspots are not obviousLocation data is not mapped or aggregated
Seasonal peaks are missedRecords are not analysed over time
Planning is reactiveNo forecast of future crime levels

The root cause was not a lack of data but the lack of a tool that turns raw records into patterns and forecasts.

Objectives:

  1. Clean and combine the police data into one reliable dataset
  2. Reveal crime patterns by type, location and season
  3. Forecast crime for the next six months
  4. Present the results in an interactive dashboard for non-technical users

3. Stakeholder Analysis

I identified the groups who would use or be affected by the dashboard and what each needs. These were defined from the business problem, as the project used public data without direct stakeholder access.

StakeholderRoleMain need
Police and law enforcementPrimary usersWhere and when to deploy officers and patrols
PolicymakersDecision-makersEvidence to target crime prevention programmes
Public safety plannersUsersSeasonal and local trends to plan interventions
The publicAffected groupFair, privacy-respecting use of crime data

Including the public as a stakeholder kept ethics and GDPR in view throughout the project.

4. Requirements Elicitation

I derived requirements from the decisions each stakeholder group needs to make.

Functional requirements

  • Show the distribution of crime by type
  • Map crime hotspots across Northern Ireland
  • Show seasonal and monthly trends
  • Rank the top crime locations
  • Forecast crime levels for the next six months

Non-functional requirements

  • Interactive and easy for non-technical users to explore
  • Built on clean, consistent data
  • Accessible online through a web link
  • Uses only data needed for the purpose, in line with GDPR data minimisation

Scope: Data.police.uk records for Northern Ireland from May 2022 to April 2025. Socio-economic data and policing interventions were outside scope.

5. Current State (As-Is) Analysis

The current state was raw monthly CSV files with no combined view. I prepared and explored the data to understand what it could reveal.

Data preparation

  1. Combined the monthly CSV files into one dataframe in Python.
  2. Removed duplicates with drop_duplicates() to prevent skewed counts.
  3. Dropped irrelevant columns such as Crime ID, Reported by, LSOA code, LSOA name, Last outcome category and Context.
  4. Cleaned locations by removing vague entries such as “On or near” and “No location”.
  5. Converted dates to datetime with pandas.to_datetime() for time series analysis.

Exploratory findings

AnalysisFinding

Hotspot heatmapCrime concentrated in Belfast and other urban centres
Crime by seasonClear seasonal peaks, with more crime in colder months
Top 10 locationsMain streets recorded the highest number of crimes

7. Options Evaluation and Recommendation

Recommendation: an ARIMA(1,1,1) time series model, delivered through a Python and Streamlit dashboard.

DecisionChoiceWhy

8. Implementation Support

I built and deployed the full solution myself in Python.

  • Data pipeline: wrote the code to combine, clean and format the police data.
  • Time series preparation: aggregated crimes by month and tested for stationarity before modelling.
  • Model build: fitted the ARIMA(1,1,1) model and produced a six-month forecast.
  • Dashboard build: brought the EDA charts and forecast into one interactive Streamlit app.
  • Deployment: published the dashboard online so stakeholders can open it from a link, with no software to install.

9. Evaluation and Monitoring

The dashboard met all four objectives, and the forecast performed reasonably well, with some error expected in real-world use.

Limitations identified

  • Missing values in Location and Outcome category could introduce bias.
  • Some crimes, such as domestic violence and sexual assault, are under-reported.
  • Data covers Northern Ireland only, which limits how far findings generalise.
  • No socio-economic or policing data, so the model cannot explain external influences.
  • ARIMA relies on past trends and cannot anticipate sudden shocks.

Conclusion

A structured BA process turned scattered public crime records into a dashboard that shows where, when and what kind of crime is likely, giving decision-makers a basis for proactive resource allocation.
